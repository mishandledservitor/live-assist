## R1. Authenticating the realtime WebSocket from the extension

**Decision**: The extension mints an ElevenLabs single-use token itself — `POST https://api.elevenlabs.io/v1/single-use-token/realtime_scribe` with the user's key in the `xi-api-key` header — and connects with `?token=…` on the WebSocket URL. A fresh token is minted for every connection, including every reconnect. This sits behind the `CredentialSource` interface (`contracts/credential-source.md`); v1's implementation is `LocalKeyCredentialSource`.

**Rationale**:
- The API accepts either the `xi-api-key` header or the `token` query parameter. The browser `WebSocket` constructor cannot set request headers, so the header route is closed to any extension context. Putting the raw API key in the URL is not an accepted auth method and would leak it into URL-shaped logs.
- Tokens are single-use and expire after 15 minutes, so one token per connection is the only correct pattern — and reconnects need a new one.
- A later company backend (ROADMAP "Company backend & distribution") issues exactly these tokens. Swapping `LocalKeyCredentialSource` for `BackendCredentialSource` changes one class; nothing else assumes the key is local (Constitution V).
- The extension declares `host_permissions` for `https://api.elevenlabs.io/*`, so the token request from an extension page is not subject to CORS.
- Key validation on save (FR-002) reuses the same call: minting a token proves the key is valid and allowed to use realtime Scribe, without touching any other endpoint. The token is discarded.

**Alternatives considered**: `xi-api-key` header (impossible from browser WebSocket); proxying through a local or remote server (adds a component and a network destination — violates Principle I/VI for v1); `@elevenlabs/client`'s `Scribe.connect` with a token (works, but see R2).

## R2. Realtime client: own thin client vs `@elevenlabs/client`

**Decision**: Write a small typed WebSocket client (`ElevenLabsRealtimeProvider`) against the documented protocol, with the `WebSocket` constructor injected so tests replay recorded message sequences. Do not depend on `@elevenlabs/client`.

**Rationale**:
- `@elevenlabs/client` 1.27.0 depends on `livekit-client` (for conversational agents) and is ~3.8 MB unpacked — a large dependency for a ~200-line protocol (Principle VI: dependencies must be justified).
- We already own capture and resampling (tab audio cannot come from the SDK's microphone helper), so the SDK would only wrap `send`/`on`. A thin client gives us exact control over reconnect, replay buffering, and error classification, and is directly fixture-testable at the message level (Principle III).
- The protocol surface we need is small and documented (below).

**Alternatives considered**: `@elevenlabs/client` `Scribe.connect` with manual chunking (`connection.send({ audioBase64 })`) — viable fallback if the protocol changes in ways the SDK hides; recorded here so switching stays a one-provider change.

**Protocol facts we rely on** (verified in docs):
- URL: `wss://api.elevenlabs.io/v1/speech-to-text/realtime` with query `model_id=scribe_v2_realtime`, `token`, `audio_format=pcm_16000`, `commit_strategy=vad`, `include_timestamps=true`, `include_language_detection=true`, optional `language_code` (ISO 639-1/3), optional `keyterms` (array), optional `vad_silence_threshold_secs`, `vad_threshold`, `min_speech_duration_ms`, `min_silence_duration_ms`, optional `secondary_languages` (array), optional `keepalive_interval_ms` (500–10000).
- Client → server: `{ message_type: "input_audio_chunk", audio_base_64, commit, sample_rate, previous_text? }`. `previous_text` is only accepted on the **first** chunk of a session (later → error) and works best under 50 characters.
- Server → client: `session_started` (`session_id`, `config`), `partial_transcript` (`text`; later partials replace earlier; empty or repeated partials are keepalives), `committed_transcript` (`text`, final), `committed_transcript_with_timestamps` (`text`, `language_code`, `words[]` with `text`, `start`, `end` in seconds, `type`, `logprob`) — sent after the committed transcript when `include_timestamps` or `include_language_detection` is true.
- Errors arrive as a message (`message_type` = error type, `error` = description) **before** the socket closes: `auth_error`, `quota_exceeded`, `unaccepted_terms`, `invalid_request`, `input_error`, `chunk_size_exceeded`, `commit_throttled`, `rate_limited`, `queue_overflow`, `resource_exhausted`, `session_time_limit_exceeded`, `insufficient_audio_activity`, `transcriber_error`, `error`.
- Audio: 16-bit PCM little-endian, **mono only**; 16 kHz recommended; chunks of 0.1–1 s. Processing starts after the first ~2 s of audio.
- Server closes the connection after 15 s without client messages (not configurable). Keepalives require us to keep sending audio — silence frames are fine.
- Manual commit is the default; VAD is recommended for live microphone input. Without commits the model auto-commits after ~36 s of audio.
- Realtime keyterms: max **50** terms, max **20 characters** each (batch allows 1000 × 50 — do not confuse them).
- No realtime diarization (words carry an optional `speaker_id`, not populated for realtime per design decision 4).
- **Unverified**: the actual session time limit duration (only the error type is documented). The design does not depend on it: any `session_time_limit_exceeded` triggers an immediate reconnect.

## R3. Commit strategy and segment timing

**Decision**: `commit_strategy=vad` with documented defaults initially (`vad_silence_threshold_secs` 1.5 as the docs' example); tunable constants, not user settings. A segment is stored from `committed_transcript_with_timestamps` (it carries words and language); `committed_transcript` only clears the in-progress line. If the timestamps message has not arrived within 2 s of its `committed_transcript`, the segment is stored with estimated times (session clock at commit) and `timing: "estimated"`.

Segment times: `startMs = session.audioOriginMs + words[0].start*1000`, `endMs = session.audioOriginMs + words[last].end*1000`, where `audioOriginMs` is the meeting-relative time of the first audio sample sent in that session. Because we stream audio continuously (including silence, R5), session audio time tracks wall time.

**Real call 2026-10-09 — silence threshold 1.0 s** (spec FR-011a): the session URL now sets `vad_silence_threshold_secs=1.0` on every session (reconnects build the URL the same way). Docs checked 2026-10-09: the API reference lists `vad_silence_threshold_secs` (number, seconds) with no default or range; ElevenLabs' commit-strategy guide uses 1.5 in its example and gives no trade-off guidance except that VAD suits live microphone input and that committing manually several times in quick succession can degrade results; third-party wrappers document a 0.3–3.0 s range (Pipecat) and defaults of 0.8 (VideoSDK) and 0.3 (Vision Agents). Evidence from the three real traces (2026-10-08, two from 2026-10-09; 50 lines, 443 word gaps): every gap between consecutive committed lines was ≥ 1.69 s, so the server committed at about 1.5 s or more of silence; gaps ≥ 1.0 s inside lines occur 15 times (8 + 5 + 2), so 1.0 s adds about one line break per three lines, all within one speaker's speech where the split is harmless; speaker handovers inside a line came with 40–420 ms gaps, which no threshold above the 0.3 s minimum separates. 1.0 s was chosen over 0.5–0.8 s because lower values cut lines at every breath (gaps ≥ 0.5 s: 29) for no handover seen in the data, and over the default because it separates pause-separated exchanges (1.0–1.5 s) before the 002 split is needed and stops depending on an unpublished default. Accuracy: shorter lines give the model less context per commit; ElevenLabs says a commit clears the accumulated transcript "without losing context", and the per-meeting key terms still apply. Latency: lines finish about 0.5 s sooner. The busy 0945 trace (40 lines, 1,890 word gaps) adds another view: 13 of its lines are 32.7–35.5 s long and end in the service's ~36 s auto-commit with 60–320 ms gaps at the cut, so in a busy call silence rarely reaches any threshold; there, gaps ≥ 1.0 s inside lines occur 45 times (one more line break per line on average), and the 002 split, not the threshold, separates speakers.

**`turn_prediction` considered (2026-10-09)**: the realtime API reference lists `commit_strategy=turn_prediction`, which "additionally commits as soon as the model predicts the speaker has finished their turn (only for models that predict turns, where it is the default)"; the `session_started` config schema for `scribe_v2_realtime` lists only `manual` and `vad`, and no guide documents turn prediction for Scribe realtime. The user's batch Scribe v2 output splits turns finely ("You will check that?" / "Yes." / "Okay."), but batch has diarization, which realtime does not (design decision 42), so that splitting cannot be had from realtime commits. Not chosen: undocumented for this model, untestable without a live key (constitution III), and a commit at a predicted turn end still could not say who spoke. A user-run check could open one session with `turn_prediction` and read `session_started.config`; until then VAD at 1.0 s stays. The ~36 s auto-commit, the 40 s replay buffer and its trimming by the committed line's last word are unaffected (more commits only trim it more often).

**Rationale**: VAD gives natural turn-sized lines and is recommended for live mic. Word timings are what 002 needs to align captions; storing them now avoids a migration.

**Alternatives considered**: manual commit on our own VAD (more code, no benefit yet); `turn_prediction` (listed in API reference, undocumented behaviour — revisit after spikes).

## R4. Reconnect without losing or duplicating lines

**Decision**: One `ReconnectingSession` per meeting (the mixed stream; revised 2026-10-08, superseded: one per stream) wraps provider sessions:
- Keeps a **replay buffer** of audio sent since the last committed segment (bounded at 40 s, above the ~36 s auto-commit). Revised red-team 2026-10-08: a commit trims the buffer only through the committed segment's last word (from `committed_transcript_with_timestamps`, relative to the session's `audioOriginMs`), never everything sent so far — frames sent after the server's commit point but before the message arrived stay for replay. A commit without word timings trims nothing (a repeated line beats a lost one). The 40 s cap is a deliberate gap, not "never loses": in an outage longer than 40 s the oldest audio is dropped and the panel reports roughly how many seconds were not transcribed.
- On drop or recoverable error: mint a new token, open a new session, send `previous_text` = last ≤50 characters of committed text on the first chunk, then replay the buffer, then resume live audio. `audioOriginMs` of the new session = meeting time of the first replayed sample.
- Committed segments are only ever appended; partials are never stored, so a session dying mid-segment cannot create a duplicate — the replayed audio produces the line once in the new session.
- Retry policy: immediate for `session_time_limit_exceeded`; otherwise backoff 0.5, 1, 2, 4, 8, 15, 15 s (≤ ~60 s total) then `failed`. Non-recoverable (no retry): `auth_error`, `quota_exceeded`, `unaccepted_terms`, `invalid_request`. `input_error`/`chunk_size_exceeded` are bugs: one retry, then fail with "internal error" (logged without audio or key).
- While reconnecting, live audio keeps flowing into the replay buffer so nothing spoken during the gap is lost (bounded by 40 s; overflow drops oldest audio and records a gap marker in the status reason).

**Rationale**: satisfies FR-019/SC-003 deterministically and is testable with fixture sequences (drop mid-partial, time limit, auth error).

## R5. Chrome MV3 capture architecture

**Decision**:
- **Start gesture & tab capture — REVISED 2026-10-08 after T012**: `openPanelOnActionClick: true` does NOT grant `activeTab` (manual check run 1: `getMediaStreamId` fails with "Extension has not been invoked for the current page"). Instead the service worker sets `openPanelOnActionClick: false`, listens to `chrome.action.onClicked`, and calls `chrome.sidePanel.open({ tabId })` synchronously in that handler; that click grants `activeTab` for the clicked tab (run 2: capture OK on YouTube and on a real Meet call, tab stays audible). Consequence for the UI: capture only works on the tab where the user last clicked the toolbar icon; on any other tab Start must tell the user to click the live-assist icon on the meeting tab first. The original text follows for history.
  - (superseded) **Start gesture & tab capture**: the toolbar action opens the side panel (`sidePanel.setPanelBehavior({ openPanelOnActionClick: true })`). The action click grants `activeTab` on that tab (action execution is a documented `activeTab` gesture; side-panel button clicks are **not** listed). On Start, the side panel asks the service worker to call `chrome.tabCapture.getMediaStreamId({ targetTabId })` (allowed in a service worker since Chrome 116). If Chrome rejects with "Extension has not been invoked for the current page", the panel shows: "Click the live-assist icon in the toolbar on the meeting tab, then press Start." A keyboard command (`commands` API, also an `activeTab` gesture) is offered as a second way to grant it. **Unverified**: that `openPanelOnActionClick` counts as action execution for `activeTab`; the early "Capture gesture" manual check in quickstart.md verifies it before the panel UI is built, and the fallback message covers either outcome.
- **Offscreen document** (`reasons: ['USER_MEDIA']`) owns all audio and the WebSocket, so transcription survives the side panel closing (FR-018) and the service worker being suspended. Only one offscreen document exists per extension, which matches "one meeting at a time". Found in Phase 5 (2026-10-08): offscreen documents get only `chrome.runtime` — no `chrome.storage` — so the key cannot be read there; the service worker mints each single-use token and returns it to the offscreen document (`RelayCredentialSource`, contracts/credential-source.md). Listeners must be registered synchronously on load (no top-level `await` first), or the service worker's first message finds no receiver.
- **Tab audio**: `getUserMedia({ audio: { mandatory: { chromeMediaSource: 'tab', chromeMediaSourceId } } })` with the stream id (single-use, expires in seconds — pass it straight through). Capturing mutes the tab for the user, so the stream is also connected to a default-rate `AudioContext.destination` to keep it audible (FR-009, SC-006).
- **Mic**: offscreen documents cannot show permission prompts. First-run setup opens an extension tab (`mic-permission.html`) that calls `getUserMedia({ audio: true })` to obtain the prompt; the grant belongs to the extension origin, after which the offscreen document's `getUserMedia` succeeds silently. If the grant is missing or revoked at Start, the mic status shows "Microphone permission needed" with a button reopening that page; the mix runs on the tab alone (US3-5). Mic constraints: `echoCancellation: true, noiseSuppression: true, autoGainControl: true` (final values from the echo spike).
- **Mixing and resampling to PCM16 mono 16 kHz — REVISED 2026-10-08 (constitution v1.1.0, decision 28)**: tab and mic feed one `AudioContext({ sampleRate: 16000 })` (Chrome resamples each MediaStream to the context rate). **Current design (since 002 T049; doc corrected red-team 2026-10-08):** the tab and mic sources go to channels 0 and 1 of one discrete `ChannelMerger` feeding the pair `AudioWorklet` (`PCM16_PAIR_PROCESSOR`), which converts each channel Float32 → Int16 LE and posts **paired** 100 ms frames (`{ tab, mic }`, 1600 samples each) to the main thread (`captureMixed` in `src/audio/capture.ts`). The pairs go through 002's mute gate (`src/core/session/mute-gate.ts`), which holds both inputs 500 ms and replaces mic frames overlapping a muted span with silence, and are then **mixed in JS** by `mixFrames` (sample-wise sum, clipped to the PCM16 range) before the one session — so muted audio never reaches the mix or the reconnect replay buffer (carry-forward note in design-decisions.md). On Meet the gate fails closed when the mute state can't be read (design decision 34); elsewhere it passes frames straight through. The mic track stays open for the whole meeting. If the mic cannot be opened, pairs carry `mic: null` and the mix is the tab alone; the capture reports the mic error. Mixing in JS was chosen over a Web Audio sum so held frames can still be silenced after the fact. Rejected: two sessions (twice the cost). (Superseded, 2026-10-08 before 002 T049: the mic went through a `GainNode` gate — `MixedSourceHandle.setMicGate` — into the same worklet input, Web Audio summed the two, and a two-input JS mixer was rejected as more code for the same sum. Superseded earlier: each stream fed its own 16 kHz context and session.) The playback path uses a separate context at the device rate so the user's audio quality is untouched. Pure conversion functions live outside the worklet and are unit-tested.
- **Continuous streaming**: frames are sent even when silent, which keeps the session alive (R2: 15 s idle close) and keeps session time aligned with wall time.

**Alternatives considered**: capture in the side panel (dies when the panel closes; panels cannot prompt for mic); `chrome.tabCapture.capture` (not available in MV3 service workers/offscreen); `getDisplayMedia` (asks the user to pick a tab every time); resampling in JS by hand (Chrome's context resampler is better and free).

## R6. Mic while muted, before the Meet adapter (spec FR-021, decided 2026-10-07)

**Decision** (user, design decision 24): no manual mic-pause control in 001. The mic is mixed in continuously while transcription runs, and the mic status shows "mute state unknown — mic is being sent". 002's Meet adapter supplies mute state through `PlatformAdapter.mute`; 002's mute gate (`src/core/session/mute-gate.ts`; 001's `setMicGate` was removed in 002 T049) silences the mic frames while muted, before `mixFrames` sums the paired tab and mic frames in JS, so the mic's contribution is silence before mixing (constitution v1.1.0; decision 30 — there is no separate mic session to pause). On Meet it also keeps the mic silenced while the mute state can't be read (design decision 34). (Superseded 2026-10-08: "sending silence or pausing the session is 002's design choice".)

## R7. Echo without headphones (spike, user-run)

**Question**: does the mic stream re-transcribe remote speakers playing from the laptop speakers, and does Chrome's echo cancellation prevent it when the remote audio is played by our offscreen `AudioContext` (not by the meeting page)?

**Design**: a dev-only extension page (`spike-recorder`, excluded from production builds) captures the tab and mic simultaneously through the real capture code and saves two 16 kHz mono WAVs per run. Runs: (1) headphones, AEC on; (2) speakers, AEC on; (3) speakers, AEC off; (4) speakers, `echoCancellation: "all"` if the Chrome version supports it (feature-detected via `getSupportedConstraints`/`getCapabilities`). `pnpm spike:echo` then streams each WAV pair through the realtime API (Node, using the key from the `ELEVENLABS_API_KEY` shell variable — never a file) and scores duplication: a mic segment counts as an echo duplicate if it overlaps a tab segment in time (±1.5 s) and their normalized token overlap is ≥ 0.6. Output: per-run JSON and a filled `spike-findings/echo.md`.

**Decision rule**: if run (2) duplicates > 5 % of remote lines, FR-028's headphones notice ships in 001 (shown at Start until "Don't show again"), and an echo-suppression filter (drop mic segments matching the rule above) is proposed as a follow-up task for the user to approve. Otherwise the notice is not shown.

## R8. Mixed Greek/English (spike, user-run)

**Design**: the user places their own clips (`*.wav`/`*.mp3`, any rate) and reference transcripts (`*.txt`, same basename) in a local, gitignored folder (`spikes/data/`). `pnpm spike:language` resamples to 16 kHz mono (ffmpeg if present, else WebAudio-free pure-TS WAV reader for WAV input), streams each clip in real time through the realtime API with four configs — auto; `language_code=el`; `language_code=en`; `language_code=el` + `secondary_languages=[en]` — and computes WER and CER (CER matters for Greek morphology) against the reference after normalization (case, punctuation, Greek tonos folded). Output: per-config table in `spike-findings/language.md`.

**Decision rule**: the config with lowest mean CER becomes the default "automatic" behaviour; if `el` + `secondary_languages=[en]` wins clearly (≥ 10 % relative), "Automatic" in the UI maps to that config for users whose settings say they speak Greek — which would be a new setting, so it is brought to the user as a spec change rather than built.

Audio clips and transcripts of real meetings never get committed (gitignored path), and the findings record only metrics and short anonymised excerpts the user approves.

## R9. Storage

**Decision**: IndexedDB via `idb` (tiny promise wrapper, ~1 kB) for meetings and segments; `fake-indexeddb` in tests. Settings and the key in `chrome.storage.local` (never `sync`) behind a `SettingsStore`. Each committed segment is written in its own transaction as it arrives (SC-004). The offscreen document is the single writer; the side panel reads on open and then follows live updates over a runtime port.

**Alternatives**: raw IndexedDB (verbose, error-prone); `chrome.storage.local` for transcripts (quota and whole-object writes; constitution says IndexedDB).

## R10. Testing strategy within Constitution III

- **Unit (Vitest, jsdom/node)**: PCM conversion, frame batching, protocol message parsing/serialization, error classification, reconnect policy (fake timers), replay buffer, segment builder and ordering, time formatting, keyterm validation, status reducer, settings validation, generic adapter contract.
- **Integration (Vitest)**: `MeetingRuntime` with one mixed source and one session; `ReconnectingSession` + `ElevenLabsRealtimeProvider` driven by a `FakeWebSocket` replaying JSONL fixtures in `tests/fixtures/elevenlabs/` (happy path, drop mid-partial, time limit, auth error, quota error); `MeetingController` + repository on `fake-indexeddb`; `LocalKeyCredentialSource` against a stubbed `fetch`.
- **End-to-end (Playwright)**: Chromium with the built extension loaded (`--load-extension`), built in `e2e` mode where `TranscriptionProvider` is the fixture-replaying `FakeTranscriptionProvider` and the capture source reads Chrome's fake media devices (`--use-fake-device-for-media-stream`, `--use-file-for-fake-audio-capture`). Covers first-run setup, Start/consent/Stop, live lines with labels, panel close/reopen, reconnect status. Real tab capture needs a user gesture on a real page and is covered by the manual check in `quickstart.md`, recorded in the spec folder (Constitution III).
- Fixtures contain no keys and no real meeting audio; recorded ElevenLabs sequences are scrubbed of `session_id` values.
